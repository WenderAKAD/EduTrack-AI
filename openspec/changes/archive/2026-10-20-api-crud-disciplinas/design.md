# Design

## Context

See `proposal.md` — Why and `specs/subjects/spec.md` for the requirements. The
constraints come from the platform and from the project rules:

- The `subjects` table exists since the `create-subjects-table` change (Tarefa
  08); `user` is the auth table, so `$auth.id` is the logged-in student.
- The Xano workspace `148813` still holds ~194 template objects that do not
  belong to EduTrack AI (see `docs/pendencias-tecnicas.md`, item 1). Every new
  API group would add one more object to clean up later.
- The frontend (Tarefa 07) is already pointed at the Base URL of the
  `AutenticacaoEduTrackIAEst` group: `https://x8ki-letl-twmt.n7.xano.io/api:JBdUmIAC`.

## Decisions

**Reuse the `AutenticacaoEduTrackIAEst` group.** The endpoints are declared
with `api_group = "AutenticacaoEduTrackIAEst"`, the group created in Tarefa 07.
A dedicated `DisciplinasEduTrackIAEst` group was considered and rejected: it
would add another object to a workspace already polluted with templates and
would give the frontend a second Base URL to configure for no functional gain.
The group's name is historical (it was born as the auth group) and already
hosts the `status` health check of the whole app.

**Exactly four endpoints.** The task lists `POST`, `GET`, `PATCH` and
`DELETE` for subjects. `GET /subjects/{id}` was considered and left out: it was
not requested, and reading a single subject is served by filtering the list.

**`auth` on every endpoint.** Each query declares `auth = ""`, so Xano
validates the JWT before the stack runs. An anonymous request never reaches the
database.

**Ownership is read from the token, never from the body.** `POST` writes
`user_id = $auth.id` directly in `db.add`; the field is not an input. `GET`
filters with `where = $db.subjects.user_id == $auth.id`. This is the security
rule of the AGENTS.md: every query filters by the authenticated user.

**`PATCH` and `DELETE` load the record before acting.** Both run `db.get` on
`{subject_id}` and use two preconditions: `notfound` when the id does not
exist, `accessdenied` when `$subject.user_id != $auth.id`. A student who guesses
another student's id gets a refusal, and the update or delete never touches the
foreign row.

**`PATCH` merges only the fields present in the request body.** Following the
Xano pattern (`util.get_raw_input` + `pick`), the data object is built from the
raw JSON keys, filtered with `filter_null` and `filter_empty_text`. Sending only
`{"name": "Algorithms"}` does not wipe `teacher` or `hours`.

**Required inputs mirror the schema.** `name`, `teacher` and `hours` are
required in the table, so they are required in `POST` (declared without `?`);
`PATCH` takes them as optional because a partial update is legal.

**Explicit table names in the stack.** `db.query subjects`, `db.add subjects`,
`db.get subjects`, `db.patch subjects` and `db.del subjects` follow the official
parser tests of the XanoScript extension, not the empty names (`""`) found in
the workspace templates.

## Risks / Trade-offs

- **Deleting a subject leaves its `academic_tasks` orphan.** The task did not
  ask for cascade rules and the Xano foreign-key behaviour was not configured
  in this change; the risk is registered here for a future change.
- **The push needs the Xano CLI** (`xano workspace push --include
  "apis/autenticacao_edutrack_ia_est/subjects*"`) and stays a manual step of the
  developer (AGENTS.md, Regra Nº 2). The endpoint ids are generated by the
  server on the first push.
- **`hours` has no upper bound.** `filters=min:1` mirrors the table; a maximum
  was not part of the requirement.
