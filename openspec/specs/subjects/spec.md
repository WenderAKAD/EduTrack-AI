# subjects Specification

## Purpose
Defines the `subjects` table — the first domain entity of EduTrack AI — and the
rule that every subject belongs to exactly one authenticated user.

## Requirements

### Requirement: Subjects table structure
The system SHALL create a `subjects` table containing exactly five fields: `id`
(auto-generated integer, primary key), `name` (text), `teacher` (text), `hours`
(integer) and `user_id` (integer, required, relationship to `user`). The table
name SHALL be `subjects`, in `snake_case`, declared at `tables/subjects.xs`. The
table SHALL carry a description stating that each row belongs to an
authenticated user through `user_id`.

#### Scenario: Table is created with the specified fields
- **WHEN** the subjects table is created
- **THEN** it exposes exactly the five fields `id`, `name`, `teacher`, `hours` and `user_id`, with `id` auto-generated as the primary key

#### Scenario: Primary key is generated by the database
- **WHEN** a subject row is inserted
- **THEN** the system assigns a unique `id` without the caller supplying one

#### Scenario: Table name follows the naming convention
- **WHEN** the table definition is read
- **THEN** the table is named `subjects` in `snake_case` and the file lives at `tables/subjects.xs`

#### Scenario: Table carries an ownership description
- **WHEN** the subjects table definition is read
- **THEN** it declares a description stating that each row belongs to an authenticated user through `user_id`

### Requirement: Subject ownership
The system SHALL require a `user_id` on every subject row, declared as a
relationship to the `user` table, and SHALL reject any insert that omits it.
The `user` table is a prerequisite of this change: it is created by
`create-user-table` and exists in Xano as table id `904016`.

#### Scenario: User creates a subject
- **WHEN** an authenticated user creates a subject
- **THEN** the system stores the row with `user_id` set to that user's id

#### Scenario: Insert without an owner is rejected
- **WHEN** a subject is inserted without `user_id`
- **THEN** the system rejects the insert and stores no row

### Requirement: Field validation
The system SHALL enforce field-level rules at the schema level, not only in
endpoints. `name` SHALL be trimmed of leading and trailing whitespace. `hours`
SHALL be an integer of at least 1.

#### Scenario: Name is trimmed
- **WHEN** a subject is created with `name` containing leading or trailing whitespace
- **THEN** the system stores the value without that whitespace

#### Scenario: Hours below one are rejected
- **WHEN** a subject is created with `hours` of 0 or a negative value
- **THEN** the system rejects the write

#### Scenario: All five fields are required
- **WHEN** any one of `name`, `teacher`, `hours` or `user_id` is omitted
- **THEN** the system rejects the write

### Requirement: Data isolation between users
The system SHALL scope every read and write of `subjects` to the authenticated
user's `user_id`, and SHALL support an efficient lookup by that column. A user
SHALL NOT read or modify another user's subject rows.

#### Scenario: User lists only their own subjects
- **WHEN** a user requests their subjects
- **THEN** the result contains only rows whose `user_id` matches the authenticated user

#### Scenario: User cannot read another user's subject
- **WHEN** a user requests a subject row owned by a different user
- **THEN** the system does not return it

#### Scenario: Isolation is enforced by the user_id index
- **WHEN** the table is created
- **THEN** it carries a btree index on `user_id`, since that column is the filter of every read

### Requirement: List the authenticated user's subjects
The system SHALL expose an endpoint `GET /subjects` that requires
authentication and returns only the subjects whose `user_id` equals the
authenticated user's id.

#### Scenario: Authenticated user lists their subjects
- **WHEN** an authenticated user sends `GET /subjects` with a valid JWT token
- **THEN** the system returns the list of subjects owned by that user
- **AND** subjects belonging to other users are not returned

#### Scenario: Request without a token
- **WHEN** a request is sent to `GET /subjects` without a valid JWT token
- **THEN** the system rejects the request with an authentication error
- **AND** the database is not queried

### Requirement: Create a subject owned by the authenticated user
The system SHALL expose an endpoint `POST /subjects` that requires
authentication, accepts `name`, `teacher` and `hours`, and stores the new
subject with `user_id` taken from the JWT token — never from the request body.

#### Scenario: Authenticated user creates a subject
- **WHEN** an authenticated user sends `POST /subjects` with `name`, `teacher`
  and `hours`
- **THEN** the system creates the subject with `user_id` equal to the
  authenticated user's id
- **AND** returns the created record

#### Scenario: Owner field is not attacker-controlled
- **WHEN** an authenticated user sends `POST /subjects` with a `user_id` in
  the request body
- **THEN** the system ignores the body value
- **AND** stores the subject with the id from the JWT token

### Requirement: Update a subject owned by the authenticated user
The system SHALL expose an endpoint `PATCH /subjects/{subject_id}` that requires
authentication, loads the subject by id, refuses the request when the subject
belongs to another user, and merges only the fields present in the request
body.

#### Scenario: Owner updates their subject
- **WHEN** an authenticated user sends `PATCH /subjects/{subject_id}` for a
  subject they own
- **THEN** the system applies the sent fields and returns the updated record

#### Scenario: Update of a foreign subject is refused
- **WHEN** an authenticated user sends `PATCH /subjects/{subject_id}` for a
  subject owned by another user
- **THEN** the system refuses with `accessdenied`
- **AND** the record is not modified

#### Scenario: Unknown subject id
- **WHEN** an authenticated user sends `PATCH /subjects/{subject_id}` with an
  id that does not exist
- **THEN** the system responds with `notfound`

#### Scenario: Partial update keeps the other fields
- **WHEN** an authenticated user sends `PATCH /subjects/{subject_id}` with only
  the `name` field
- **THEN** the system updates `name`
- **AND** `teacher` and `hours` keep their previous values

### Requirement: Delete a subject owned by the authenticated user
The system SHALL expose an endpoint `DELETE /subjects/{subject_id}` that
requires authentication, loads the subject by id and refuses the request when
the subject belongs to another user.

#### Scenario: Owner deletes their subject
- **WHEN** an authenticated user sends `DELETE /subjects/{subject_id}` for a
  subject they own
- **THEN** the system deletes the record

#### Scenario: Delete of a foreign subject is refused
- **WHEN** an authenticated user sends `DELETE /subjects/{subject_id}` for a
  subject owned by another user
- **THEN** the system refuses with `accessdenied`
- **AND** the record is not deleted

#### Scenario: Unknown subject id
- **WHEN** an authenticated user sends `DELETE /subjects/{subject_id}` with an
  id that does not exist
- **THEN** the system responds with `notfound`
