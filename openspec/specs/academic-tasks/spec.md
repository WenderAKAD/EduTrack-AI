# academic-tasks Specification

## Purpose
Define the `academic_tasks` table, which stores the student's academic
obligations (homework, exams, assignments) and the link between each task and a
subject.

## Requirements

### Requirement: Academic tasks table structure
The system SHALL create an `academic_tasks` table with exactly six fields: `id`
(auto-generated integer primary key), `title` (text), `description` (text),
`due_date` (date), `status` (text) and `subject_id` (integer, required,
relationship to `subjects`). The table name SHALL be `academic_tasks`, in
`snake_case`, declared at `tables/academic_tasks.xs`, and SHALL carry a
description stating that each row belongs to a subject through `subject_id`.

#### Scenario: Table is created with the specified fields
- **WHEN** the academic_tasks table is created
- **THEN** it exposes exactly the six fields `id`, `title`, `description`, `due_date`, `status` and `subject_id`, with `id` auto-generated as the primary key

#### Scenario: Primary key is generated by the database
- **WHEN** a task row is inserted
- **THEN** the system assigns a unique `id` without the caller supplying one

#### Scenario: Table name follows the naming convention
- **WHEN** the table definition is read
- **THEN** the table is named `academic_tasks` in `snake_case` and the file lives at `tables/academic_tasks.xs`

### Requirement: Task belongs to a subject
The system SHALL require a `subject_id` on every task, declared as a
relationship to the `subjects` table, and SHALL reject any insert that omits it.
The `subjects` table is a prerequisite: it is created by
`create-subjects-table` and must exist before `academic_tasks` is pushed.

#### Scenario: Task is linked to a subject
- **WHEN** a task is created for a subject
- **THEN** the system stores the row with `subject_id` set to that subject's id

#### Scenario: Insert without a subject is rejected
- **WHEN** a task is inserted without `subject_id`
- **THEN** the system rejects the insert and stores no row

### Requirement: Field validation
The system SHALL enforce field-level rules at the schema level. `title` and
`status` SHALL be trimmed of leading and trailing whitespace. `due_date` SHALL
be stored as a calendar date. All six fields except the auto-generated `id`
SHALL be required.

#### Scenario: Title is trimmed
- **WHEN** a task is created with `title` containing leading or trailing whitespace
- **THEN** the system stores the value without that whitespace

#### Scenario: Due date is a calendar date
- **WHEN** a task is created with a due date
- **THEN** the system stores it as a date

#### Scenario: Required fields cannot be omitted
- **WHEN** any of `title`, `description`, `due_date` or `status` is omitted
- **THEN** the system rejects the write

### Requirement: Ownership inherited from the subject
Ownership of a task SHALL be inherited from its subject: a task belongs to the
user who owns the `subjects` row it points to. The table SHALL NOT duplicate a
`user_id`, and reads SHALL scope to the authenticated user through the subject.

#### Scenario: Ownership comes from the subject
- **WHEN** a task points to a subject owned by a user
- **THEN** the task is considered owned by that user, without a `user_id` column on `academic_tasks`

#### Scenario: Reads scope through the subject
- **WHEN** tasks are listed for the authenticated user
- **THEN** only tasks whose subject belongs to that user are returned

#### Scenario: Efficient lookup by subject
- **WHEN** the table definition is read
- **THEN** it declares a btree index on `subject_id`
